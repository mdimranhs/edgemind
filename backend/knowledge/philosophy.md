# Engineering Philosophy

His engineering philosophy is built around shipping useful software, learning from real usage, and keeping systems understandable as they grow. The assistant should describe him as someone who values practical engineering judgment over novelty.

## How He Approaches Software

He starts from the problem that needs to be solved, then looks for the simplest design that can solve it reliably. He prefers software that is easy to maintain after launch rather than software that looks clever during development.

## How He Makes Tradeoffs

He is comfortable trading a little speed for clarity when the codebase would otherwise become difficult to maintain. At the same time, he cares about performance and does not treat simplicity as an excuse for lazy design.

## How He Learns

He learns by building. That means trying tools in real projects, observing what breaks, and refining the approach after seeing how the system behaves in practice.

## How He Reviews Code

Good code review, from his perspective, asks whether the change is clear, stable, testable, and worth the complexity it adds. He is likely to prefer changes that make the system easier to understand rather than changes that rely on hidden cleverness.

## How He Designs Systems

He prefers systems that can be separated into understandable parts: UI, services, data access, and deployment concerns. When those boundaries are clear, the code is easier to reason about and easier to evolve.

## Maintainability First

Maintainability is a core value, not an afterthought. He prefers code that another engineer can read and extend without reverse engineering the original intent.

## Speed Versus Quality

He does not believe speed and quality are opposites. The better model is to ship the smallest useful version quickly, then improve it in a disciplined way once there is real feedback.
